# Koreos v0.2.0 — 6 platforms, cross-platform Pong, live demo

*May 30, 2026*

Koreos v0.2.0 is available on Maven Central. Over five sprints, the library has grown from 3 to **6 platforms** (macOS, iOS, Android, Windows, Linux, Web) and ships a complete technical demo: **Pong playable everywhere with the same `commonMain` code**. Live demos are accessible in the browser.

---

## What v0.2.0 brings

- **3 new backends**: Win32 (Windows), X11 + Wayland (Linux), JS + Wasm (Web)
- **9 modules published to Maven Central**: `koreos-core`, `koreos-appkit`, `koreos-uikit`, `koreos-android`, `koreos-win32`, `koreos-x11`, `koreos-wayland`, `koreos-js`, `koreos-wasm` + facade `koreos`
- **Cross-platform Pong**: a single `PongGame.kt` running on all 6 platforms via wgpu4k
- Public API backward-compatible with v0.1.x — only `RawWindowHandle` variant additions

---

## Sprint 3 — Win32 backend (Windows)

The Windows backend is built on **Panama FFM (JDK 25)** via kextract, with no JNI or JNA. The Win32 message loop supports all three `ControlFlow` modes:

- **Poll** → `PeekMessageW` (non-blocking, ideal for continuous rendering)
- **Wait** → `GetMessageW` (blocks until the next system message)
- **WaitUntil** → `MsgWaitForMultipleObjectsEx` with a computed timeout

The `WndProc` is allocated via `Arena.ofShared` — process lifetime, never released, which prevents any use-after-free when Windows calls the procedure after the Kotlin stack has unwound. DPI handling uses **PerMonitorV2**: `SetProcessDpiAwarenessContext` at startup, then `GetDpiForWindow` on each `WM_DPICHANGED` to recompute `scaleFactor` and dispatch `ScaleFactorChanged`.

## Sprint 2 — Web backend (JS + Wasm)

The Web event loop is driven by **`requestAnimationFrame`** (RAF): each frame computes the delta from the previous frame and passes it to `ApplicationHandler.onRedrawRequested`. Mouse and touch input is unified in `DomEventMapper`, which converts DOM `PointerEvent` into Koreos `WindowEvent` — a single code path for mouse, stylus, and touch, on both desktop and mobile.

Two separate modules coexist: `koreos-js` (Kotlin/JS IR, `jsBrowser` target) and `koreos-wasm` (Kotlin/Wasm, `wasmJsBrowser` target), with a shared `koreos-web-common` layer (`pagehide`/`pageshow` lifecycle, canvas resize via `ResizeObserver`). The `koreos` facade exposes the corresponding `actual` implementations without any API change.

---

## Sprint 4 — Linux backend (X11 + Wayland)

The Linux backend auto-detects the active compositor at startup: attempts a Wayland connection (`wl_display_connect`), falls back to X11 if `WAYLAND_DISPLAY` is absent or the connection fails. The `KOREOS_LINUX_BACKEND` environment variable allows an explicit override.

Both backends follow the **lazy `tryCreate` pattern**: FFM bindings for Xlib and libwayland-client are loaded inside a `try/catch Throwable` — if the system library is absent (e.g., a Wayland-only system without `libX11.so`), the backend fails cleanly without a JVM crash. The Wayland loop combines `poll` on the `wl_display_get_fd` file descriptor with a wake-up `eventfd` (0 ms timeout in Poll mode, blocking in Wait mode), avoiding busy-looping while remaining responsive.

---

## Sprint 5 — Cross-platform Pong

`PongGame.kt` lives entirely in `commonMain`: not a single line of platform-specific code in the game logic. `GameState` tracks the ball, paddles, and score in normalized coordinates (0.0–1.0). `PongRenderer` uses wgpu4k to render 5 2D quads (player paddle, AI paddle, ball, two score digits via a hardcoded bitmap font). The AI (`PongAi`) tracks the ball with a configurable **lag coefficient** — fast enough to be a challenge, slow enough to be beaten.

Input is unified: arrow keys on desktop, right-side touch zone on mobile and web. `requestRedraw` is called on every `aboutToWait`, targeting 60 fps on all platforms.

---

## Notable technical points

- **Poll mode across backends**: `PeekMessageW` (Win32) / `XPending` (X11) / `poll fd=0ms` (Wayland) / RAF delta (Web) — same semantics, native implementations
- **Lazy Linux FFM**: `try/catch Throwable` on symbol loading — no crash on a Wayland-only system without `libX11`
- **`Arena.ofShared` WndProc**: process lifetime, never closed — the Win32 callback remains valid for the entire execution
